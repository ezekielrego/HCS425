# Test evidence

`mvn clean verify` runs protocol, store, real TCP integration, replication, and ten-client benchmark smoke tests. The benchmark suite is separate so measured results are not confused with unit-test timing.

Required runtime evidence is generated by the scripts:

* `results/csv/performance-results.csv` — fixed 2,000-operation workload at 1, 2, 5, 10, and 20 clients.
* `results/csv/stress-performance-results.csv` — fixed 10,000-operation capacity workload at 1, 50, and 100 clients using 128 bounded workers.
* `results/csv/fault-tolerance.txt` — client-abort scenario and post-abort request check.
* `results/charts/` and `results/charts/stress/` — SVG charts generated from the measured CSV files.
* `results/screenshots/` — Xvfb screenshots from the running JavaFX application, including light-mode operation, 50-client, performance-control and server-log captures.

The benchmark reports mean, median, p95, throughput, speedup relative to the measured one-client run, efficiency, and errors. Total operations and operation mix remain identical across client counts.

Observed runtime evidence:

* `mvn -q verify` passed all module tests.
* Required 1/2/5/10/20-client benchmark completed 2,000 operations at each count with 0 errors.
* Capacity stress benchmark completed 10,000 operations at both 50 and 100 clients with 0 errors using 128 bounded workers.
* The 50-client run achieved 8,217.51 operations/second with 30.370 ms p95 latency; the 100-client run achieved 8,365.37 operations/second with 52.917 ms p95 latency.
* Fault test kept the server running, completed 9 unaffected clients, and accepted a replacement client after an aborted socket.
* Three-process cluster test returned the same PUT value from replica ports 5051 and 5052.
* JavaFX launched under Xvfb `:99`; dashboard, operation, performance, logs, and replication PNGs were captured at 1280×800.
